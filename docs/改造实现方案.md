### 2.6 已交付的根因结论与第一轮修复（2026-10-06）

**根因（诊断数据由 `app/scripts/diagnose-atlas-remap.mjs` 用真实布局函数产出）**

1. **图集表面按"槽位数"分配，而非按"可达专辑数"。** 显示池是 9 列 × 48 行 = 432 槽位，
   于是封面图集恒为 4096×6912 RGBA ≈ **108 MB**；每绘制一个瓦片都置
   `atlas.needsUpdate` → 整张 108 MB 重新上传。
2. **列轴与行轴的重映射周期不同，这正是症状的来源。** `visibleCell` 用
   `nearestOccurrence(池内列值, 相机中心, 9)`（列轴周期 9）与 `(…, rows)`（行轴周期 48）：
   - **跨列一步**：必有一整组（48 个槽位）从"相机后方"翻到"相机前方"，整组专辑换新
     → 成批 `paintTile` + 整表上传；
   - **同列一步**：周期 48，常规步进几乎不重映射（实测 0–9 个槽位）。
   实测表：跨列一步 `48 槽位 / 12–48 张新封面`，同列一步 `0–9 槽位`。
3. **封面缩放跑在主线程**：多兆像素原图经 `drawImage` 缩到 1024 缩略图，
   一次跨列集中触发一整列的"解码 + 缩放"，恰好落在相机起步那一帧。

**已实施（commit `perf(atlas): …`）**

| 改动 | 效果 |
|---|---|
| 新增 `poolAlbumCapacity(rows)`：由"列内专辑数 ≤ min(rows, n)"推出同帧可达专辑数的**精确上界**，图集按此分配 | 79 张曲库：4096×1280 = **20 MB**（1/5.4）；12 列 × 7 张：16 MB（1/6.8） |

### 2.7 第二轮修复（2026-10-06）：脏矩形上传 + 详情栏增量更新

上一轮之后用户反馈"卡顿有所改善但依旧存在"，本轮按上表第 3 条的**第一候选**继续做，并补上第二处主因。

**已实施 —— 图集脏矩形上传（上文候选一的落地）**

原本登记的理由是"需真机验证色彩空间与兼容性"，因此本轮先把三件事从 three r183 源码里查清，再动手：

- `renderer.properties.get(texture).__webglTexture` 是裸 GL 句柄；首帧渲染前为 `undefined` → 必须回退整面上传。
- 绑定要走 `renderer.state.bindTexture(gl.TEXTURE_2D, handle)`，**不能**用裸 `gl.bindTexture`：后者会让 three 的 `currentBoundTextures` 与实际绑定不一致，下一次绘制沿用错纹理。three 自己就是这么绑的。
- `uploadTexture()` 每次上传都**无条件重设** `UNPACK_FLIP_Y_WEBGL`/`UNPACK_PREMULTIPLY_ALPHA_WEBGL`/`UNPACK_ALIGNMENT`/`UNPACK_COLORSPACE_CONVERSION_WEBGL`，故照抄取值（1 / 0 / 4 / `NONE`，因为 `colorSpace = SRGBColorSpace` 与工作色彩空间同原色）不会留下脏状态。
- `getContext()` 的静态类型是 WebGL1｜WebGL2 联合，联合上只有 `texSubImage2D` 的 `ArrayBufferView` 重载；源码形式须经 `WebGL2RenderingContext` 取（three 只请求 `'webgl2'`，运行时确实是 WebGL2）。
- **纵向落点**：canvas 带 `UNPACK_FLIP_Y_WEBGL` 上传，子矩形只翻转自己那一块，故 canvas 行 `y` 落 `H - h - y`。提取为 `atlasSubRectY()`，并与 `writeTile` 给着色器的 UV（`1 - (row+1)/rows`）**互相独立推导同一位置**，`check-music-scene` 逐行比对。

**未采纳上文写过的 `copyTextureToTexture`**：它要求源是纹理而非 canvas，为每个瓦片再造一张源纹理只会把问题搬走；`texSubImage2D` 直接吃 canvas，是更短的路。

**已实施 —— 详情栏就地增量更新（本轮新发现的第二处主因）**

`renderDetail()` 每次换专辑都 `innerHTML` 重写整根阅读栏 → 每次重建带 `backdrop-filter: blur(18px)` 的标签栏（合成器重新生成模糊层）+ 重解析档案面板与 8 行参数表 + 指示器 `offsetLeft` 带来的强制同步布局。改为 `detailSkeleton()` 建一次骨架、只写 5 个变化区域；标签栏文案恒定、只写选中态，选中态未变时跳过指示器读取。约束：`h1` 必须仍是 `#album-detail-content` 的直接子元素（4 条 `> h1` 规则），故上半区不能包裹；档案面板的稳定父层用 `.archive-mount{display:contents}`。

**已量化后主动放弃**：`scene.ts` 每帧约 432 个 `visibleCell` + 432 个模板字符串 + 1 个 `Set`，`music-camera.ts` 每帧 12–20 个 `Vector3`，约 10 µs/帧量级，比一次 21 MB 上传或一次强制布局低两个数量级。

**验证**：`tsc --noEmit` 通过；`vite build` 106 模块；`check-music-scene`（含落点交叉验证）通过；线上层真实联网 4/4 命中且 Apple Music 零请求。

**仍需你在真机上确认**：封面是否显示成**正确的专辑**、方向是否正常（纵落点算错的唯一表现）。若错误，把 `CoverAtlas.uploadTile()` 返回值改成恒 `false` 即回到整面上传，正确性不变、只损失性能。

### 3.7 【已补实现】线上补录层 —— 第四层来源（2026-10-06）

§3.4 当初只给了"人工补录 + 资料库 `description`"两层。实交付时补上了**线上实时补录**这一层：
即一张从没被任何数据源描述过的专辑，也能在用户**主动点击后**拿到发布背景，
而**不需要预先跑全库抓取**（这是 §3.4 未覆盖的第三种路径）。

**四层优先级（严格有序，高者胜）**

| 层 | 来源 | 落盘位置 | 允许写外部事实 |
|---|---|---|---|
| 1 人工 | `content/album-archives.json`（手写，必带 `sources`） | 随仓库走 | ✅ 唯一允许"不联网就写外部事实"的层 |
| 2 线上 | **QQ 音乐 / 百度百科 / MusicBrainz**（第三阶段才补 Apple Music 商店） | `<数据目录>/album-online/*.json`，TTL 30 天 | ✅ 但必须随内容显示来源名 + 链接 + 许可 |
| 3 资料库 | `album.description` + `descriptionSource`（既有抓取管道） | `music-index.json` | 继承既有 `descriptionSource` |
| 4 派生 | 本地算术（曲目数 / 时长 / 年份跨度 / 格式分布） | 不落盘 | ❌ 只允许本地能算出来的事实 |

**服务端**：新增 `scripts/album-online.mjs`（导出 `AlbumOnlineResolver`）与路由 `GET /api/album-online/:id`。

- **只访问白名单主机**（`PROVIDER_HOSTS`）；单次抓取 6s 超时、维基 2.5s、整体预算 12s、
  两次请求之间 1100ms 间隔（对 MusicBrainz 的礼貌限流）。
- **熔断**：连接类失败累计到阈值后，本进程对该来源跳过 30 分钟，落盘 `_breakers.json` 且**跨实例生效**。
  真实全库实测：维基百科被本机 DNS 污染，熔断让它 79 张专辑只付出 **1 次超时**（其余 77 张直接 `skipped`）。
- **429 / 503 单次退避重试**（MusicBrainz 官方文档明写 503 = back off；实测《七里香》首次 503、重试即命中），
  `500` 不重试、直接记为 `failed` 并把 HTTP 码写进界面提示。
- **匹配必须过阈值**：标题 / 艺人 / 年份打分，`score >= 8`（满分 11）才采用。
  实测 US 商店对《范特西》返回 12 条完全无关结果（`2CELLOS / Score`），代码正确全部拒绝。
  **不要为了提高命中率去放宽这个阈值**——宁可显示空态，也不能把别人的专辑背景写到用户脸上。
- **门控**：资料库设置中的 `onlineEnabled` 默认 `false`，其语义是"**扫描后自动**补录"，不是"手动点击"。
  手动入口走 `?consent=1` 显式授权，两者互不影响（否则默认关闭会让手动按钮变成死键）。
- **确定性装配**：来源并发执行，但装配顺序固定为**计划顺序**（`qq → baike → musicbrainz`，第三阶段才是 `itunes`），
  因此同一张专辑在缓存过期前后得到的句子顺序完全一致。
- **空态也是结果**：`status` 取 `ok` / `empty` / `error` / `disabled`；未命中的来源在界面上逐条列出**未采用原因**，不静默吞掉。
  两种"没内容"要分开说：**全部来源不可达** → `error`，理由就是传输错误（用户对标签无能为力）；**有来源回答了"没找到"** → `empty`，此时顶层文案给的是可操作建议（补全名称/歌手/年份），某个商店的报错留在它自己那一行。

**客户端**：`src/music-archive.ts` 的 `AlbumArchiveContext` 增加 `online` 字段，
`resolveAlbumArchive` 在人工层命中后短路、否则在资料库层之前插队。
线上命中时 `status: "online"`、面板标记「线上补录」；未命中则退回资料库/派生，并把"未采用任何内容"+ 失败原因写进提示。
详情页档案面板底部给出 `线上补充详情与背景 ↗`（读取中 → `正在读取线上资料…`，读毕 → `重新读取线上资料 ↗`），
旁边另给「在百度搜索更多 ↗」搜索链接；资料库设置面板另给 `逐张补充专辑详情与背景 ↗` 的批处理入口。
点击后**只替换 `.album-archive` 子树**（`outerHTML` + 重跑解密函数），不重播整个详情页的入场动画。

## 4. 需求 C —— 顶部"小白条"：详情 ⇄ 歌词切换控件

> 位置基准：`参考-详情页与小白条位置.png` 红圈处 = 详情页顶部中央（overline 上方居中）。

### 4.1 形态

- 小圆角白条（建议 ~48×6px、圆角 3px），**轻微朦胧辉光**：柔和 box-shadow 光晕 + 可选 backdrop-blur 底衬；质感对齐现有玻璃拟态语言（`glass-reveal.ts`、`music-theme.css` 变量）。克制：不闪烁、不过亮、不呼吸过快。

### 4.2 状态机（核心，必须严格实现）

```
[D 详情态]（默认：显示专辑详情）
   │ hover ──→ 微浮动：幅度很小的上下浮动（建议 translateY ±2px、周期 ≥3s）+ 辉光轻微呼吸
   │ click ──→ [L 锁定态]：浮动停止；拖拽被抑制（防误触）；再点解锁回到之前状态
   │ 按住向下拖（pointerdown + move ↓）
   ▼
[T 过渡态 p: 0→1]
   · 详情面板：随 p 向下滑动 + 逐渐淡出
   · 歌词面板：自上而下逐渐显现，最终占据详情原位置
   · 小白条本体：沿 p 从顶部锚点平滑移动到底部锚点（不消失、不淡出）
   │ 松手且 p > 0.5 ──→ 弹簧收尾 → [Y 歌词态]（条停在歌词页下方）
   │ 松手且 p ≤ 0.5 ──→ 弹簧回弹 → [D]
[Y 歌词态]（条位于歌词页下方：drag ↑ 反向播放同一动画，p 1→0 → [D]）
```

### 4.3 触发与映射细则

- 指针事件：`pointerdown` 起拖 + `setPointerCapture`；`pointermove` 的 dy 映射进度 p（带阻尼/lerp，跟手但不生硬）；`pointerup` 按阈值弹簧收尾；全程 rAF 驱动。
- 双面板动画**只动 `transform: translateY()` + `opacity`**（可给退隐面板叠加轻微 `filter: blur()` 增强"退后"层次）；**禁止**在拖拽路径触发布局属性（width/height/top/left）或 DOM 重建。
- 条的位移与双面板进度共用同一个 p，三者严格同步。
- 键盘可达（本应用键盘驱动）：条聚焦时 `Enter`/`↑`/`↓` 切换两态，动画走同一弹簧收尾路径。
- 详情页 `上一张/下一张` 换片时若处于歌词态：保持歌词态，歌词数据换新（预热规则见 §5.4）；`Esc` 返回浏览页时整个组件随详情销毁并释放资源。

### 4.4 性能约束

- 空闲浮动/hover 动画纯 CSS（`transform`/`opacity`/`filter`，GPU 合成），不用 JS 定时器。
- 拖拽期间：不发请求、不解码图片、不重建面板 DOM、不触发 GC 大对象分配。
- 与其他动画共享 rAF 心跳（对齐 `motion.ts` 现有体系），禁止多循环叠加。

### 4.5 验收

- [ ] 状态机五态（D / hover / L / T / Y）全部按表工作；拖拽全程 ≥55fps 无跳变
- [ ] 歌词态下条可见且可反向拖回；锁定态不响应拖拽
- [ ] 辉光克制、风格统一；窄窗口不错位（responsive.css 断点）

### 4.6 【已精修】小白条的"精美"与"优雅"落到了哪些参数（2026-10-06）

初版小白条是**一个** `<span>` + 一条 CSS 关键帧（上下 4px 平移）。功能上满足 §4.1，
但观感偏"塑料"，且鼠标移入/移出会看到幅度突变。本版把"精美"和"优雅"拆成**可验收的参数**逐项落实：

**① 三层光学堆叠**（而不是一块会动的色块）

| 层 | 尺寸 | 处理 | 作用 |
|---|---|---|---|
| `.detail-switch-halo` | 132×44 | `blur(9px)`、`opacity .20` | 最外层大气辉光，决定"朦胧" |
| `.detail-switch-glow` | 84×24 | `blur(4px)`、`opacity .34` | 中间过渡层，决定"发光" |
| `.detail-switch-core` | 52×8 | 双段渐变 + 顶部镜面高光 `rgba(255,255,255,.46)`、`opacity .50` | 实体白条本体，决定"精致" |

三层各自的模糊半径与不透明度不同，叠加后才出现从"实心"到"化开"的连续过渡；
单层加大 box-shadow 无论怎么调都做不出这个层次。

**② 三套不同周期的浮动，且初始相位错开**

| 层 | 关键帧 | 周期 | 延迟 | 幅度 |
|---|---|---|---|---|
| core | `switch-float` | 3.8s | −0.6s | ±1.6px |
| glow | `switch-drift` | 4.6s | −1.2s | ±2px |
| halo | `switch-breathe` | 7.4s | −2.4s | ±2.8px + `scale .97 → 1.05` |

**关键在相位与周期都不同**：三层永远不会同步到同一个极值，于是看上去是"一直有轻微变化"而不是"在打拍子"。
若三层共用周期，无论多慢都会显出机械感——这是"优雅"与"整齐"的分界。

**③ 一道 6.6s 的掠光**：`.detail-switch-core::after` 是一条 16px 宽的高光，沿白条横向掠过（`switch-glint`）。
周期远大于浮动周期（6.6s vs 3.8s），两者不同步，因此掠光出现的位置每次都不重复。

**④ hover 从"纵向拉伸"改为"等比放大 + 拉长"**：`scale 1.06 1.25`。
原先直接拉长 y 轴会让模糊层的椭圆畸变，观感廉价；改为横向也放大后，比例关系保持一致。
同时 `glow .34 → .58`、`halo .20 → .34` —— 变亮的是**外两层**（即"光变强"）而不是白条本体（不是"白条变白"）。

**⑤ 锁定 = 暂停而非移除**：见 §6.1 偏离第 6 条。`animation-play-state: paused` 让三层停在当前帧，
锁定前后逐像素连续，没有跳变。锁定态的不透明度为 core `.94` / glow `.18` / halo `.10`
（本体变实、外层收敛，读作"已被按下并固定"）。

**⑥ 按下是不对称的**：拖拽中 core 取 `scale 1.02 0.72`、`transition-duration: 150ms`（比弹回短），
读作"被压扁"；松手后回到 3.8s 的浮动周期，读作"回弹"。

**⑦ 甩动（fling）**：`pointerup` 时若采样速度 `|v| > 1.1`（阈值）就直接判定去向，
不再依赖"过没过中线"；速度上限 ±2.6，并作为初速度交给弹簧收尾，因此快速轻甩也能一次到位。
速度用指数平滑采样（`v = v*0.6 + instant*0.4`）并对每帧 dt 做 8ms–200ms 的夹取，
避免掉帧或停顿后算出荒谬的瞬时速度。

**⑧ 键盘可达**：`:focus-visible` 时按钮本身 `outline: none`，焦点环画在胶囊体上
（`0 0 0 1px var(--accent), 0 0 14px 3px var(--accent)`），与"辉光"是同一套语言，不引入第二种高亮样式。

**⑨ `prefers-reduced-motion`**：四套动画与全部 transition 一并移除，回到静态白条。

## 5. 需求 D —— 歌词动效（AMLL 思路 + 懒渲染）

### 5.1 参考

https://github.com/Steve-xmh/applemusic-like-lyrics —— 只借鉴**实现思路**：弹簧物理滚动、逐字卡拉OK渐变高亮（有逐字时间轴时）、非活跃行模糊 + 降透明度、活动行放大强调。**不引入其源码依赖**（技术栈不匹配、许可需单独评估），自行实现同思路渲染器。

### 5.2 歌词数据来源（当前代码库**完全没有**歌词通道，需新建）

优先级从高到低：

1. **内嵌标签**：扫描期用 `music-metadata`（已在依赖中）读取 USLT/LYRICS 歌词标签（SYLT 逐字时间轴存在时一并保存），写入 `library-index.json` 对应曲目；
2. **同名 .lrc**：音频同目录同名 `.lrc` 文件（兼容增强 A2 逐字格式 `[mm:ss.xx]<字时间>`）；
3. **空态**：都没有 → "暂无歌词"（样式对齐专辑介绍"待补充"空态）。

- 时间轴对齐：复用 `music-player.ts` 既有播放状态流（`syncTransportScrub` ~1058 已在接收 player state），取 currentTime 驱动行高亮；**禁止**另起轮询或独立音频解析。
- 歌词解析器落点：新建 `src/music-lyrics.ts`（解析）+ `src/music-lyrics-pane.ts`（渲染）+ 配套 CSS，风格命名对齐现有 `music-*` 模块。

### 5.3 动效规格（AMLL 风格要点）

- 容器：歌词面板占据详情内容区（位移由 §4.2 的 p 驱动）。
- 行状态：
  - 活动行：scale/字重强调 + 渐变扫过（有逐字时间轴按字推进；无则整行平滑淡入强调）；
  - 非活动行：`blur(≈2px)` + opacity ≈0.4，离活动行越远越弱；
  - 行间滚动用弹簧跟随（自实现 spring，参数手感对齐现有 `motion.ts`）。
- 行可点击跳播为可选项；若实现，必须走 `music-player.ts` 既有 seek 通道。

### 5.4 懒渲染时序（性能核心，硬性要求）

```
打开专辑 / 进入详情  ──→ 【不】构建歌词面板：零 DOM、零解析、零监听
首次按住小白条向下拖（pointerdown）
   ──→ 执行一次性预热：
       ① 解析 LRC/标签 → ② 构建 DOM → ③ 一次性测量并缓存各行位置 → ④ 首帧渲染
   ──→ 目标：预热总耗时 ≤ 100ms（常规 ≤60 行歌词）
   ──→ 预热期间拖拽进度 p 照常推进（歌词面板最晚在 p≈0.2 时已可见，用户无感知）
预热只做一次，同专辑内面板常驻（切换态不销毁）
换专辑（keepDetail 换片）→ 释放旧歌词数据与 DOM → 回到"不构建"状态，下次拖拽再预热
```

### 5.5 性能约束

- 只动 `transform/opacity/filter`；行 DOM 上限：>200 行时只渲染可视区 ± 缓冲（虚拟化或截断）。
- 单 rAF 循环；面板不可见（p=0 或已 Esc 离开）时**暂停**循环并移除 `will-change`。
- 测量一次、缓存复用；仅在 resize / 换专辑时重测。禁止拖拽帧内 `getBoundingClientRect` 循环。
- 离开详情页释放解析结果与监听器（与 §4.3 销毁路径一致）。

**参数设置模块**：新增 `src/lyrics-settings.ts` + `lyrics-settings.css`，作为 token 的**单一定义处**：真实面板（`LyricsPane.setStyle`）与面板内预览（`lyricsMarkup` 的 `#lyric-preview`）共用 `lyricTokenList()`，因此预览不可能与播放页不一致。11 项参数 + 两个取色块（空串 = 跟随主题，而不是钉死今天的主题色）+ 恢复默认；存 `rhine-lyric-preferences` —— **刻意不写进 `rhine-music-preferences`**，以免触碰新装环境上没有 quality 字段的 `untouchedQuality` 迁移分支。两个值必须留在 JS 侧：`pitch` 同时是滚动步长，`delayMs` 折进播放时钟。

`check-music-lyrics` 增加一条**接线契约**：从 `lyrics-settings.ts` 抽出的每个 `"--ly-*"` token 都必须被 `music-lyrics-switch.css` 读取 —— 拼错属性名在构建期完全不可见，只会表现为"滑块没反应"。同理，样式表里**不留** `--ly-blur`：`blur(0px)` 仍会生成 filter 层，所以"高亮行 `none`、其余行按距离加模糊"只能由渲染器决定，值也在渲染器里缩放。

**与方案的三处偏离（均为实现中发现更优解，理由如下）**

1. **歌词不进索引，改走 `GET /api/lyrics/:trackId` 按需读取**（方案 §5.2 原写"扫描时抽取"）。
   理由：歌词若写进 `music-index.json` 会让该文件随歌库线性膨胀，而它每次扫描都要整读整写；
   歌词又不像封面需要预生成缩略图，唯一成本就是一次标签读取，而面板只在用户真的开始拖动时才需要它。
   副作用是**改 `.lrc` 无需重新扫描即生效**，对用户更有利。
2. **"点击锁定"只冻结浮动，不禁止拖动**（方案 §4.2 未明确二者关系）。
   理由：若锁定同时禁止拖动，而拖动是唯一的切换手势，用户点一下就把自己锁死在详情态。
   现实现：锁定 → 浮动停止 + 条形转为实心标记；拖动始终可用，退出路径永不丢失。
3. **`[data-d]` 属性替代 `.active/.near/.far` 三个类**（方案 §5.3 只描述了视觉结果）。
   理由：每行改类需要 3–4 次 `classList.toggle`；改成写 `data-d` 与 `--blur` 后每行只需 2 次写入，
   且分级虚化可以直接用 `filter: none` 跳过远处行，避免为看不见的行分配 filter 图层。
4. **线上层插在资料库层之前，而非与之并列**（§3.7 为新增层，原方案无对应条款）。
   理由：用户要的是"补全详情"而不是"二选一"。插队后人工层仍绝对优先，资料库描述转为**补充**而非替代，
   并且两者都有出处时去重合并，界面上一条来源都不丢。
5. **`onlineEnabled` 默认 `false` 保持不变，但手动「线上补充详情与背景」不受它约束**。
   理由：默认关闭是上游既有的隐私取舍，应当保留；但若手动按钮也受它约束，默认状态下这个功能就等于不存在。
   因此拆成两条通道——自动批处理看开关，手动点击走 `?consent=1` 显式授权。
6. **锁定态用 `animation-play-state: paused` 而不是 `animation: none`**（§4.2 只写"浮动停止"）。
   理由：`none` 会让三层光晕**瞬间归位**，点击的一帧出现可见跳变；`paused` 让光晕停在当前帧，
   点击前后完全连续。这条是"优雅流畅"的硬要求，不是可选优化。

**性能约束的落实位置（方案 §4.4 / §5.5）**

- 拖拽每帧只写：条形的 `transform`、`#detail-surface` 的 `transform` + `opacity`、歌词面板的 `--reveal`；
  歌词内部每帧只写 `.lyrics-track-line` 的 `--shift` 与活动行的 `--p` / `--line-p`。
- `clip-path` 用于逐字高亮的裁剪副本，不触发排版与文字重排；
  `will-change` 只加在三个真正会动的容器上，行节点不加。
- 歌词零预热：打开专辑不产生任何歌词 DOM/解析/监听；预热在首次 `pointerdown` 触发，
  一次抓取 + 一次解析 + 约 60 行挂载，实测量级远低于 100ms 预算（网络为 127.0.0.1，解析为纯字符串处理）。
