## 一、缺陷 1：播放结束后不自动接下一首

### 定位过程

**第 1 步 — 建 red-capable loop**

复用 `app/scripts/check-music-player.mjs` 已有的受控环境 harness（假 DOM + 假音频元素 +
`env.advance()` 推进时钟），写一个最小复现：放一首 → 触发结束 → 断言是否走到下一首。

结果：**通过**。浏览器播放路径与 `eof` 事件路径都正常。

> 这一步的价值在于**排除**：接歌逻辑本身没问题，问题在别处。

**第 2 步 — 扩大怀疑面（三次"也通过"）**

- 扩测三种歌曲衔接模式（`fade-out` / `fade-in-out` / `gapless`，v0.4.1 新代码，
  首要怀疑窗口）→ 通过
- `repeat-one` 单曲循环 → 通过
- 单曲队列边界 → 通过

**第 3 步 — 插桩，暴露测试污染**

给 `subscribe()` 加打印后发现：某次测试之后，**后续测试全都不再走预期通道**。

根因是 `getNativePlayback()` 是**模块级单例**，绑定假宿主后 `available` 永久为真，
`<audio>` 那条路被顶掉了。于是有测试在"通过"，但它们验的是错的东西。

修复：把原生测试**拆成独立文件**；正式脚本内让"无宿主测试必须排在第一位"，
并在文件里写明这个顺序是**承重的**（有注释）。

**第 4 步 — 真正的根因**

```ts
// 修复前 app/src/player/music-player.ts 构造期
this.native = getNativePlayback();
if (this.native.available) {          // ← 此刻宿主还没到
  this.native.subscribe(...);         // ← 整段订阅被跳过
  this.value.backend = "native-libmpv";
}
```

WebView2 外壳是在**页面加载之后异步**注入 `window.__rhinePlayerControl` 的，
所以 `MusicPlayer` 构造那一刻，宿主通常还不存在。`available` 为假 →
**整个事件订阅从未建立**。此后播放结束，原生层发来的 `eof` 事件**没有任何接收者**，
歌曲就停在末尾。

浏览器（用 `<audio>`）复现不出来，是因为那条路走 `audio.addEventListener("ended")`，
在页面里就能注册——这解释了为什么第 1、2 步全"通过"。

### 修复

`music-player.ts`：改为**无条件订阅**，并用新增的 `onAvailable()` 在宿主迟到时补挂。

```ts
this.native.subscribe((event) => this.onNativeEvent(event));   // 先订阅，不等宿主
this.native.onAvailable(() => {                                // 宿主到了再补正状态
  if (this.disposed) return;
  this.value.backend = "native-libmpv";
  this.native.ping();
  this.emit();
});
if (this.native.available) { this.value.backend = "native-libmpv"; this.native.ping(); }
```

`native-playback.ts`：新增 `onAvailable(listener)`——已就位则立即回调，
否则挂进等待队列，在 `refresh()` 首次发现宿主时一次性放行。

订阅在普通浏览器里是惰性的（没有宿主就没有事件），所以**不增加任何开销**。

### 回归测试

新建 `app/scripts/check-music-player-native.mjs`，**独立进程**，两则：

1. 无宿主时浏览器路径仍能接下一首
2. **宿主迟到注入后，`eof` 仍必须接下一首** ← 这则就是缺陷本身，旧代码必红

## 二、缺陷 2：只有第一首有歌词，第二首起不显示

### 定位过程

**第 1 步 — 先排除服务端**

用真实曲库跑 `lyrics.mjs` 的 `readLyrics()`：**8/8 首**都能读出
`source=uslt`，逐首独立 `parseFile`，无跨曲目复用。服务端没问题。

**第 2 步 — 发现测试盲区**

`check-music-lyrics.mjs` 只覆盖纯模型（解析、时间轴、`splitUnits`），
**`LyricsPane` 组件本身没有任何测试 seam** —— 这是一处架构发现。

**第 3 步 — 自建最小 DOM 桩，首次复现成功**

写 `FakeElement`（补 `remove()` / `classList` / `appendChild` 等）驱动组件：

```
setTrack('track-1') → trackId = 'track-1'   ✓
setTrack('track-2') → trackId = 'track-1'   ✗ ← 复现
```

还发现第二种形态：当 `options.current()` 返回 `undefined` 时，
面板**完全不加载任何东西**，停在上一首或留空。

**第 4 步 — 根因**

```ts
// 修复前 music-lyrics-pane.ts
setTrack(info) {
  this.info = info;
  if (this.reveal > 0) void this.prepare();   // ← prepare 会丢开 info
}
prepare() {
  const info = this.options.current();        // ← 重新推导，覆盖刚设的那首
  ...
}
```

`setTrack()` 把装载任务转交 `prepare()`，而 `prepare()` **不看 `this.info`**，
而是回头去问 `options.current()` 要目标。当外壳的当前曲目还没同步过来
（切歌瞬间的常态），这次二次读取拿到的仍是**上一首**，于是面板一直装第一首。

### 修复

`music-lyrics-pane.ts` 两处：

```ts
prepare(): Promise<void> {
  const info = this.info ?? this.options.current();   // 已设曲目优先
  if (!info) return Promise.resolve();
  ...
}

setTrack(info) {
  if (!info) { this.clear(); return; }
  if (this.info?.trackId === info.trackId) { this.info = info; this.syncCredit(); return; }
  this.clear();
  this.info = info;
  if (this.reveal > 0) void this.load(info);          // 装载"传进来的那首"
  else this.syncCredit();
}
```

原则：**装载谁，就装 `setTrack` 交过来的那一首**，不再回头重新推导。

### 回归测试

新建 `app/scripts/check-music-lyrics-pane.mjs`，三则：
切第二首装载自己的歌词 / `current()` 取不到时不得留空面板 / 面板关闭时切歌、
打开后读当前曲目。前两则对旧代码变红。

## 四、源码按功能区域解构

### 结果

`app/src` 从平铺 **99 个文件** 变为六个区域 + 根 4 文件：

| 区域 | 数量 | 职责 |
|---|---|---|
| `core/` | 25 | 与音乐业务无关的通用底座：样式、动效、解密、质量、小工具 |
| `shelf/` | 39 | 唱片架三维场景：排布、相机、导航、灯光、档案、搜索、标题 |
| `viewer/` | 11 | 模型查看器渲染管线：离屏、景深、锐化、玻璃揭示 |
| `boot/` | 8 | 启动动画：品牌出现、轨道飞行、时序编排 |
| `player/` | 7 | 播放内核：音频、libmpv 通道、接歌过渡、播放顺序 |
| `lyrics/` | 5 | 歌词：时间轴模型、面板组件、设置面板 |
| 根 | 4 | `main.ts` `archive-main.ts` `music-app.ts` `vite-env.d.ts` |

划分标准只有一条：**改一个功能时，要动的文件应该都躺在同一个目录里。**

### 方法：两遍重写

**第一遍**（`restructure-src.py`）处理 `import` / `export` 说明符。
**第二遍**（`restructure-src-pass2.py`）专治第一遍漏掉的**非导入形式的路径引用**：

- `new URL('../src/x.ts')` 这类平铺字面量
- `sourceModule(..., { './theme-transition.ts': ... })` 的 **override 键**
  —— 键必须与模块源码里的说明符**逐字匹配**，改了路径不改键就静默失效
- 模板串 `` `../src/${name}` `` 动态拼出的路径

### 踩的坑（三个）

1. **第一遍漏改 src 内无扩展名导入**：`resolve_target` 用 `.exists()` 查文件系统，
   但文件在解析前**已经被搬走**，永远找不到 → 改为查归类表补候选扩展名。
2. **`app/scripts` 基础目录传错**：`rewrite()` 传了 `SRC` 而非 `SCRIPTS`。
3. **第二遍仍漏 3 处**：`check-music-lyrics.mjs` 里有三个 `read()` 用
   `` `../src/${name}` `` 拼路径 → 改为经 **`AREA` 映射表**解析，
   并在 `app/src/README.md` 里写明"文件挪了目录要同步改这张表"。

### 必须守住的一点

**CSS 副效果导入的顺序决定层叠优先级，重写时逐字保留**（用 `paste` 对比验证过）。
顺序变了，样式会以难以察觉的方式错位——不会有任何报错。

### 新增文档

`app/src/README.md`：各区域职责、依赖方向（`core/` 不认识任何人；
`lyrics/` 不认识 `shelf/`；跨界走 `music-app.ts` 中介）、
新增文件该放哪的判定顺序、改完必跑什么。

## 六、两个缺陷的共同点（值得记住）

两处都是**初始化竞态**，形态一致：

> 某个条件在"构造那一刻"为假，代码就**静默地不做接线**，此后再也没有第二次机会。

- 缺陷 1：宿主没到 → 不订阅 → `eof` 无人接收
- 缺陷 2：`current()` 没同步 → 重新推导 → 装错曲目

两者都**不会报错**，都只在真实的时序下才现形，所以都只能靠
**能变红的回归测试**锁死——这也是本轮两个新测试脚本存在的全部理由。
