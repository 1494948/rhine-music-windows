### 0.3 之前的"真机验证"其实没有压到封面这条路径

测试数据目录 `playground/rhine-music-local-mod-data` 的 `artwork/` 里**只有 16 个文件、合计 4.6 MB**，
而曲库声明 **79 张专辑**。也就是说历次验证里绝大多数专辑走的是「暂无封面」占位分支。
设计工况是 **4000×4000 的 JPEG（16 MP，解码后 64 MB RGBA）**，最大的一张就是 4000×4000。

**结论**：封面解码/缩放/上传这条路径从未被真正压测过 —— 而 §2 会把卡顿指到这里。

### 0.4 本机测量能力的边界（诚实交代）

本轮我想用"装上探针的构建产物 + 真实浏览器"直接测出长帧归因，**没有做成**，原因有三，都已定位：

1. **浏览器进程被沙箱中和**：`msedge.exe --version` 零输出、退出码 0；`--headless=new --dump-dom` 同样零输出；
   用独立 `--user-data-dir` 启动后配置目录连 `SingletonLock` 都不生成。连试三次（bash / Node spawn / 越过沙箱）
   均无效，服务端访问日志里**一条浏览器请求都没有**。上一轮会话能做到，本轮环境变了。
2. **`http_proxy=http://127.0.0.1:9646` 会截获回环**：`curl http://127.0.0.1:5173/api/health` 返回
   `502 upstream connect failed`。要测本地服务必须 `curl --noproxy '*'`。
   顺带一个方法论结论：**数据源可达性不能用 curl 测**（走的是沙箱出口代理，结论与用户家庭宽带无关），
   必须用 Node 内置 fetch（undici 默认不读 `http_proxy`）—— §5 就是这么测的。
3. 后台服务会被中途回收，无法保证跨多次工具调用常驻。

**因此本轮的定位是「先找到问题 + 做计划」，找到问题靠代码证据与定量推算，不靠运行时采样。**
测量台（`playground/rhine-perf/`）已写好并保留：探针、收集器、启动器都在，
**等环境允许时或由用户在真机跑一次即可拿到长帧归因**（见 §6 的 P1 验收）。

## 2. 问题 A：换风格残留卡顿 —— 根因定位

### 2.1 已被排除的（有证据，不必再查）

| 嫌疑 | 现状 | 证据 |
|---|---|---|
| 图集整面上传 21 MB×N | 已改脏矩形上传，**且已接线**（不是死代码） | `cover-atlas.ts:271 attachRenderer` / `scene.ts:404` 调用；产物中两处命中 |
| 详情栏整栏 `innerHTML` 重建 | 已改就地写 5 个区域 | `72d7c4a` |
| 每帧场景遍历 432 槽位 | 折算约 10 µs/帧，比一次上传低两个数量级 | `72d7c4a` 的量化结论 |

### 2.2 仍然存在的三处，按代价从大到小

**A1 · 每张封面要解码两次，且第二次是"高质量"重采样** —— `cover-atlas.ts:385 decodeThumbnail`

```
createImageBitmap(blob)                        // 第一次：全尺寸解码（4000×4000 → 64 MB RGBA）
createImageBitmap(blob, { resizeQuality:"high", resizeWidth/Height })  // 第二次：16 MP → 1 MP 高质量重采样
```

- 图块实际只需要 **256 px**（`tileWidth = min(256, maxTextureSize/columns, …)`），
  却按 `MAX_THUMBNAIL = 1024` 解码 —— **白付 16 倍像素**。
- 一次换风格会新建最多 `poolAlbumCapacity()` 个图块，`POOL_LANES` 有 9 条泳道，
  79 张曲库求和后 ≈ **79** ⇒ 最坏一次切换要做 **~158 次解码**，其中 79 次是高质量重采样。
- 没有任何预取：第一次走到某个风格，那一整列的封面全部落在切换那一刻。

**A2 · 缩略图缓存上限与像素量严重不匹配** —— `cover-atlas.ts:15`

`IMAGE_CACHE_LIMIT = 96` × 1024² × 4 B = **约 402 MB 常驻位图**。这既是内存压力，
也意味着滑过几个风格之后必然出现 GC 尖峰 —— 表现为"偶发、不规律"的卡顿。

**A3 · 带抬起的卡片换片时，每次重建出画卡片** —— `scene.ts:874`

```ts
const group = this.model.clone(true);          // 克隆整个专辑模型组
this.covers?.snapshot(cover);                  // 1024² 画布 + CanvasTexture（POT，带 mipmap）+ material.clone()
canvas 1024×440 标签画布 + drawImage(this.labelCanvas)
```

每换一张专辑做一遍：一次 `model.clone(true)`、两个画布、两个纹理（≈5–6 MB 上传 + mipmap 生成）。
`lift.value > 0.0001` 即触发，所以**浏览态下的每一次换片都会走到这里**。

### 2.3 为什么"有所改善但依旧存在"能自洽

`72d7c4a` 修的是**上传**（21 MB 整面 → 262 KB 子矩形，约 80×），
但 A1 的解码突刺、A2 的内存压力、A3 的每片重建**一个都没动**。
三者的量级恰好比整面上传低、比一帧的预算高 —— 正是"明显改善、依然能感觉到"的形态。

## 3. 问题 B：歌词动效距 AMLL 的差距（用户明示"以画面为重"）

现状（已核实）：每帧只写两个属性 —— 整轨 `--shift` 与活动行 `--p`；
`music-lyrics-switch.css` 里唯一与歌词有关的关键帧是 `lyric-float`；

| AMLL 有 | 本包现状 | 差距说明 |
|---|---|---|
| 逐字独立变换（位移/字重/字距随唱到位置变化） | 整行一个裁剪值 | 字的边缘"一刀切"，没有逐字呼吸 |

| 按距离分级虚化 | 有（`--blur` 分级，可用 `filter:none` 跳过远处行） | 已对齐 |
| 间奏/纯音乐段的律动提示 | 无 | 长间奏期间画面是静止的 |
| 逐行缩放 | **有意未做**（担心每帧重新光栅化） | 用户已授权"性能可舍"⇒ 可以重新评估 |

## 5. 问题 D：国内数据源实测矩阵（本轮真实测过）

**方法**：Node 内置 fetch（undici，不读 `http_proxy`），与应用运行时同一条网络路径。
只做 GET，9 s 超时。被测专辑《范特西》/ 周杰伦。

### 5.1 已验证可用（可直接接入）

| 源 | 状态 | 耗时 | 结论 |
|---|---|---|---|
| QQ音乐·建议 + 专辑详情 | 200 / JSON | 225 / 100 ms | 已在用 |
| 百度百科·开放 API | 200 / JSON | 199 ms | 已在用 |
| MusicBrainz | 200 / JSON | 711 ms | 已在用 |
| Apple Music 商店 | 200 / JSON | 443 ms | 已在用 |
| **网易云音乐·搜索** `/api/search/get/web` | 200 / JSON | 207 ms | **可新增**，返回专辑 id/名称/歌手 |
| **网易云音乐·专辑详情 `/api/v1/album/{id}`** | 200 / JSON | 189 ms | **可新增**，返回完整专辑 JSON（含简介与封面） |
| Discogs `/database/search` | 200 / JSON | 1701 ms | 可选，慢；作为 MusicBrainz 补充 |
| 维基数据 wikidata | 200 / JSON | 2673 ms | **与上一轮结论冲突**（上一轮记为不可达）；本次可达但慢，应按 best-effort 处理 |

### 5.2 已验证不可用（记录在案，避免下轮重测）

| 源 | 结果 | 原因 |
|---|---|---|
| zh.wikipedia.org | 9 s 超时 | 确认不可达，保持移除 |
| 网易云 `/api/album/{id}` | 200 但 `code:-462` | 风控要求绑定手机；**改用 `/api/v1/album/{id}` 即绕开** |
| 酷狗（m 站/复合搜索/www） | 证书主机名不匹配 / 404 / SPA | 无可用结构化接口 |
| 咪咕 m.music.migu.cn、music.migu.cn | 返回 HTML | 无公开 JSON 接口 |
| 豆瓣 | v2 接口 404（已关停）；站点返回通用页 | 不可用 |
| 5sing、Amazon Music | TLS 失败 / 连接重置 | 不可达 |
| 知乎、百度/Bing 搜索 | 403 / HTML | 搜索页只能做"跳转链接"兜底，不能做数据源 |

**结论**：真正值得新增的只有 **网易云音乐**（搜索 + `/api/v1/album/`）。
它恰好补上现有四家最缺的「中文专辑简介」——QQ音乐有简介但覆盖不稳定，百度和百科偏"词条"。

## 6. 实施计划

### P0 · 让修复真正到达用户（成本最低、收益最大）

1. 重新构建 → 回灌 `app/dist` → 逐文件 MD5 校验（沿用既有回路与 `MSYS2_ARG_CONV_EXCL='*'`）
2. `scripts/package-windows.mjs` 增加**入口哈希一致性断言**：包内 `index.html` 的入口
   与 `app/dist/index.html` 不一致即退出码 1
3. 重建 `releases/rhine-music-local-mod/v0.3.0-local.2/`，更新使用说明与发布说明
4. 验收：包内起服务，`/api/health` 正常；用 `--noproxy '*'` 拉 `/` 与 `/assets/<入口>`，
   确认哈希与仓库一致；`使用说明` 里写明"本包对应提交号"

### P1 · 换风格卡顿彻底解决

| 步骤 | 做法 | 预期 |
|---|---|---|
| P1-1 | 建立**两级缩略图**：图块只吃 256 px（改为 `createImageBitmap` 一次解码直接带 `resizeWidth/Height` 到 256，`resizeQuality:"low"`）；详情页大图另走 1024 px 单张按需解码 | 解码像素量降 **16×**，且**不重复解码** |
| P1-2 | 重算缓存上限：按"实际驻留像素"设上限（例如 256 px 档 256 张 ≈ 67 MB），不再用固定 96 条 | 消掉 402 MB 的内存压力与 GC 尖峰 |
| P1-3 | **空闲预取**：首屏稳定后（`requestIdleCallback`）按当前风格相邻顺序，用低优先级逐张预热 256 px 缩略图；换风格时先命中缓存 | 把突刺从"切换那一刻"移到"用户没在操作时" |
| P1-4 | 去掉 A3 的每片重建：`snapshot()` 的 1024² 纹理与 `model.clone(true)` 改为**复用池**（预分配 2–3 个出画槽位，循环使用），并把 `CanvasTexture.generateMipmaps` 关掉 | 每次换片省一次克隆 + 两个纹理上传 |
| P1-5 | 验收：真机（用户机或环境允许时）跑 `playground/rhine-perf/` 探针，`ArrowRight`/`ArrowLeft` 各 10 次，要求 **p95 帧间隔 ≤ 20 ms、> 50 ms 的帧为 0**；纹理上传单次切换 ≤ 2 MB | 可量化，不靠感觉 |

> ⚠️ P1-1 会降低图块锐度（256 px 用 low 质量重采样）。因为 tiles 在 3D 里本身只有 256 px，
> low 与 high 的差别在最终画面里不可见；但**详情页大图必须仍用 1024 px high**，两者不能混用。

### P2 · 歌词动效对齐 AMLL（用户已授权牺牲性能）

按"视觉收益/实现风险"排序，逐项可独立验收：

1. **逐字层改为逐字独立变换**：现在是一个裁剪百分比，改为每字一个 `--g`（0→1），
   字重、字距、垂直位移随 `--g` 变化；用 `clip-path` 保留锐利字形（不重新光栅化）
2. **行进入/退出**：新行从下方 12 px + `opacity 0` 进入，旧行向上退场；用 `--line-in` 类 + 一次 transition
3. **活动行过冲**：变为活动行时给一次轻微 overshoot（弹簧，约 180 ms）
4. **间奏律动**：连续超过 N 秒的无歌词区间显示呼吸点阵（纯 CSS，零 JS 定时器）
5. **重新评估逐行 scale**：用户已明确"性能可舍"，测一轮再决定是否加回（加 `will-change` 前先量化）
6. 全部新增项都必须挂进 §4 的参数模块，可关、可调 —— 不能出现"改不了的动效"

### P3 · 歌词参数模块体验补全

1. 参数分组：字号与版式 / 颜色与高亮 / 动效 / 时间
2. 每项独立复位（滑块右侧一个回位图标）＋ 分组复位
3. 预设三套：`克制`（现状）、`Apple Music`、`AMLL`
4. 导入 / 导出 JSON（一键复制、粘贴恢复）
5. 预览区可选"用哪首歌的哪一行"，并支持"跟随播放"开关

### P4 · 数据源扩充与自检

1. 新增网易云音乐适配器：`/api/search/get/web` 定 id → `/api/v1/album/{id}` 取详情；
   **只用 GET、只读公开字段、白名单主机加 `music.163.com`**
2. 把 Discogs 与 Wikidata 作为 `best-effort` 末位来源接入（各自独立超时与熔断，失败只影响自己那一行）
3. **新增一个可达性自检脚本**（`check-music-online-sources.mjs`）：逐主机报告
   `status/耗时/是否 JSON`，并写进 `check:music`；这样"某天某源挂了"能被自动发现而不是用户先发现
4. 用 Node（undici）而不是 curl 做可达性判定，并把这条方法论写进 `PROJECT.md` 的坑
5. 覆盖率回归：真实全库 79 张重跑一次，报告各源贡献与总命中率（上一轮基线：39/79 = 49.4%）

## 7. 需要你确认的四点

1. **P0 是否立刻做**：重建一个约 515 MB 的分发包（含全新的 P1–P4 修复）。
   建议顺序是 P0 先做一次"仅含已完成修复"的包，让你先确认细线与参数模块确实在了，
   再叠 P1–P4。
